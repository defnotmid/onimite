# fframes (Rust) vs onimite (Odin + Lua): same examples, 1:1

Every fframes example is ported to onimite in `examples/fframes/`, and both
sides render the same video: the same size, fps, frame count and duration.
The tables below are generated by `tools/bench.sh facts` on a published
onimite release; `bench/facts.json` holds the same numbers for the films and
the site, so none of them is typed by hand.

**What you need to reproduce this.** The ports use fframes' own media, which
is not committed: `examples/fframes/fetch.sh` fetches fframes into
`third_party/fframes` (the commit pinned in `third_party/fetch.sh`) and
copies the media next to the ports. Then `tools/bench.sh facts [TAG]`
downloads the release TAG (default: the latest), checks it against the
release's SHA256SUMS, builds fframes' examples and measures; `tools/bench.sh
setup` measures the installs. For work on onimite or on a port,
`tools/bench.sh facts build/onimite` runs the same race on a local build
(into `.work/bench`, leaving `bench/` alone) and `tools/bench.sh visual`
compares chosen frames side by side. The script is table-driven: `PAIRS` at its top names each fframes crate and binary and the
onimite script.

Notes on the pairs:

- fframes runs each example as it ships: its renderer (Skia on Vulkan, or
  its CPU renderer) and libx264 at the example's CRF. onimite runs as it
  ships: SDL_GPU (Vulkan here) and Vulkan Video H.264 at constant QP 23.
  Quality isn't matched, so file sizes aren't an equal-quality comparison.
- `shaders` and `neon_triangle`: fframes' default CPU renderer draws no
  shader layers, so its time understates the work.
- `motion_graphics`, `mg_install` and `mg_quote`: fframes' binaries run with
  `concurrency: 1`, as shipped.
- `shader_mode`: its soundtrack is not in fframes' repository, and both
  sides play the same 31 s 220 Hz stand-in (`examples/fframes/fetch.sh`).
- `pixel_memory` picks its photos at random on fframes' side, so its
  pictures differ by design and its PSNR is low.
- The PSNR and SSIM compare the two whole videos in 4:2:0. Most of the
  difference is glyph edges and mid-animation frames, where the two sides'
  easings differ slightly (named easings are cubics on onimite's side).

## Method

- fframes: `cargo build --release -p <example crate>` in
  `third_party/fframes`, one crate at a time as a user builds it (built
  together, cargo would merge their features); each binary runs `<bin>
  render -o out.mp4` from its example's directory, where it finds its media.
- onimite: the release's Linux binary, downloaded from GitHub and checked
  against the release's SHA256SUMS and `--version`, never a local build;
  `onimite render examples/fframes/<example>/video.lua -o out.mp4`, on the
  release's own scripts (its tag's `examples`, `bench` and `skills`,
  exported, with the fetched media linked in), whatever the working tree
  holds.
- A warm-up renders each example's first second on both sides (media and
  shaders in the caches); then every row runs three times, round by round,
  and each number is the median of the three, with the wall time's min and
  max.
- Every run waits for an idle machine (other processes using under half a
  core, the GPU under 10% busy) and is run again when other work used more
  than half a core on average while it ran (the machine's busy CPU time less
  the run's own and the kernel threads'; an idle desktop and its sessions
  use a third to two thirds of one, another job shows several: runs kept
  with other work over half a core came out up to 65% slower than their
  row's best, under it up to 13%), or the GPU for more than
  a tenth of the run (every other process's GPU engine time, from the
  kernel's per-client counters, `drm-engine-*` in `/proc/<pid>/fdinfo`: a
  GPU-bound render shows there while its CPU stays low). Other work on the
  machine makes a run take longer, not measure wrong. Right before each
  timed run a tiny untimed frame wakes the GPU: one idle for half a minute
  takes about 0.1 s to wake, which isn't either program's work (it put
  0.34 s instead of 0.20 s on the saga's frame at random).
- fframes' side is measured again only when the fframes commit, the CPU,
  the GPU or Mesa changes; otherwise its numbers and videos from the last
  measurement are reused, and the table says when each side was measured.
  A pair fframes fails to render isn't timed on either side.
- A release that changes what only some rows do (a 3D library: the rows
  that draw in 3D) can be measured for those alone (`BENCH_ROWS`): every
  other row keeps the numbers of the release that measured it, on the same
  machine (a different CPU, GPU or Mesa measures everything again), and each
  onimite figure in `bench/facts.json` carries the release that measured it
  (`tag`); the line above says which rows were measured again.
- GNU `/usr/bin/time` gives the wall time, the CPU time (user + sys) and the
  peak RSS. Wall time includes process start, loading media and fonts, and
  the final mux. Frame counts, sizes and durations come from ffprobe; a pair
  whose two videos differ in any of them isn't compared.
- Release sizes: each archive as downloaded, and the sum of the files in
  it.
- Installs (`setup`): each tool installed fresh into an empty directory
  with its own HOME, as its README says; the sum of the files, each hard
  link counted once. fframes at its pin, in an Ubuntu 22.04 container with
  the packages its README lists (and freetype's and fontconfig's, which
  Skia links): rustup's minimal stable toolchain; the crates `cargo install
  --locked cargo-fframes` and the first build add; the first build of `cargo
  fframes new` (target/ and what it caches in HOME); `cargo tree` counts the
  crates built for Linux. Remotion's latest release on Node.js LTS: Node
  unpacked; node_modules of remotion, @remotion/cli, react and react-dom
  (the packages on disk, not the lockfile's optional ones for other
  platforms); the Chrome Headless Shell `remotion browser ensure` fetches.
  System packages and download caches aren't counted. They're measured
  again when fframes' pin or Remotion's latest version changes.

## Caveats

- One machine, one GPU. The hardware encoder bounds onimite on short,
  simple videos, while fframes runs x264 on every core.
- The race measures `render` only. fframes' editor and onimite's preview
  aren't compared.
